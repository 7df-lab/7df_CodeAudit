## 1. 总体形态与设计原则

```
┌──────────────────────────────────────────────────────────────┐
│ 展现层（本文档范围）                                          │
│                                                              │
│  Web控制台(React SPA)   CLI(Go单二进制)   IDE插件(VSCode+JB)   │
│          │                    │                 │            │
│          └────────────┬───────┴─────────┬───────┘            │
│                       ▼  HTTPS/REST(JSON) ▼                    │
│              gateway-service :8080（JWT + 限流 + 转码）         │
└────────────────────────────────┬─────────────────────────────┘
                                 ▼ gRPC（内部）
                      7 微服务（01 §4；ADR-175/197）
        ◀──── Webhook 出站（storage NotificationService，回调整合方）
```

**六条设计原则（贯穿全文）：**

| # | 原则 | 依据/说明 |
|---|------|----------|
| P1 | 网关是唯一入口 | 03 §1.1；客户端不直连 5005x gRPC 端口（服务间 mTLS 口径） |
| P2 | 不定义新数据结构 | 页面消费的每个字段都能溯源到 proto message；UI 专用展示态（如"风险分"）禁止——没有依据的数字不展示（ADR-129） |
| P3 | 后端能力缺失 = UI 如实降级 | gRPC Unimplemented → UI 显示"能力未接入"而非隐藏入口或假数据 |
| P4 | 展示即数据 | 列表/详情字段与 REST 响应字段一一对应（protojson UseProtoNames，snake_case） |
| P5 | 尊重限流与分页基线 | 07 §7 单用户 50 req/min：默认 page_size=20（proto L227）、列表防抖、无自动轮询风暴 |
| P6 | 五模式一等公民 | 04 §3 五模式在任务创建/详情/报告中有一致的模式标识与差异化视图 |

## 2. 认证、会话与权限

### 2.1 会话流（数值见 03 §4 / 07）

```
登录页 ──POST /v1/auth/login──▶ {access_token(30min), refresh_token(7d)}
  │ 内存持有 access；refresh 存 localStorage（V1，见开放问题 Q3）
  │ 401 → 静默 POST /v1/auth/refresh → 重放原请求；refresh 失效 → 回登录页
  └─ 所有请求带 Authorization: Bearer；网关校验后向下游注入 x-user-id/x-user-role
```

- **登出**：`POST /v1/auth/logout`（撤销 access）；CLI/IDE 用同一端点。
- **口令/种子账号**：V2.1（ADR-205）起密码一律 bcrypt、注册/改密/重置链路齐备（Q1 已按人类新指令更替，见 §11）；登录页提供「去注册」入口。

### 2.2 权限模型（消费 proto，不新增角色定义）

角色语义来自 JWT claims `user_role` 与 `UserService.ValidatePermission`（proto L1209-1210：resource_type × action）。UI 按下表做**显示与入口级**门禁（服务端仍是权威，UI 门禁只为体验）：

| resource_type | action | UI 能力 | 可见角色 |
|---|---|---|---|
| project | create/update/delete | 项目 CRUD 按钮 | admin |
| project | read | 项目列表/详情 | 全部 |
| task | create/execute | 创建任务、Start/Cancel/Retry | admin, developer |
| task | approve | Submit/Approve/Reject 审批按钮 | admin（审批人≠创建人，前端提示） |
| finding | update | verdict triage（确认/误报） | admin, auditor |
| report | read | 报告查看/下载 | 全部 |
| user | update | 用户管理页 | admin |
| knowledge | read | ↪KG/RAG 页已随 ADR-197 删除，仅存 Skills 页（数据源=dsh-runtime） | 全部（S06/S09/S10 只读口径，04 §4） |

> V1 角色集合以 project-service 种子数据为准（admin/auditor/developer/Viewer），角色→resource×action 的映射表在 project-service 侧实现（ValidatePermission 已有结构，无 proto 变更）。

### 3.3 核心页面详设

**① 任务创建向导 `/tasks/new`（P0，五模式分流 04 §3）**

```
Step1 选择项目（下拉，仅本人可访问项目）
Step2 选择模式（五卡片，各带一句语义与预估耗时口径 07 §8）：
      A 纯SAST | B 纯AI | C SAST+AI融合★推荐 | D AI增强SAST | E SAST+AI对比（ADR-186 五模式）
Step3 模式差异化参数：
      A/C/D/E → sast_tools 多选（选项来自 GET /v1/tools——
              只展示 ValidateToolConfig 返回 valid=true 的工具，P3 原则：
              codeql 等无执行映射的工具显示"解析器就绪/执行未接入"置灰）
      全部  → project_path（V1 为网关宿主机路径 + 下拉历史，Q4 见开放问题）
      D     → review_config
Step4 确认页 → POST /v1/tasks（gateway 自动生成 request_id 幂等键）
      → 引导跳转 /tasks/:id
```
约束：创建前调 `ValidateToolConfig` 逐工具探测，任一失败给黄色警示但不阻断（04 §6 降级语义）。

**② 任务详情 `/tasks/:id`（P0，进度监控）**

- **阶段时间线**：`GET /v1/tasks/{id}` 的 `stages[]`（proto TaskStage：stage_id/type/status/started_at/completed_at/error_message）渲染为步骤条；FAILED 阶段展示 error_message 原文（P4：展示即数据）。
- **实时进度（V1 = 轮询）**：每 3s `GET /v1/tasks/{id}/progress`（proto TaskProgress.overall_percent + stages）；任务到终态自动停止轮询。轮询而非推送的理由：WatchTaskProgress 在 task-service 为显式 Unimplemented（诚实口径），SSE 网关代理留 V1.1（§3.4）。
- **终态处理**：COMPLETED → 结果入口；FAILED/DEAD → error_message + 重试按钮（Retry 仅 DEAD 可用，对齐 proto L863）；TIMEOUT → 说明文案。
- **状态流转按钮**按 §2.2 权限与状态机可见（非法转换按钮置灰而非隐藏，悬停说明当前状态原因——UI 教学状态机）。

**③ 发现列表 `/tasks/:id/findings` 与全局 `/findings`（P0）**

- 数据源：`GET /v1/findings?filter={task_id}&pagination={}`（游标分页 03 §5，"加载更多"而非页码跳转）。
- 列（全部为 proto UnifiedFinding 字段，P4）：severity 徽标 / cwe_id / title / source_tool / location(file:line) / ai_verdict / confidence。
- 筛选：severity、ai_verdict、source_tool、cwe_id（proto FilterRequest 结构，不自造筛选项）。
- 行内 triage（有 finding:update 权限）：确认/误报/需人工 → `PUT /v1/findings/{id}/verdict`；批量选择 → `POST /v1/findings/verdict:batch`。
- verdict 值域即 proto AIVerdict 6 值枚举（含 NEEDS_MANUAL），UI 中文映射表维护在 web 层常量（纯展示翻译，非新结构）。
- 10k+ 行：Ant Table 虚拟滚动；服务端游标，前端不整表拉取。

**④ 发现详情 `/findings/:fid`（P0，triage 工作台）**

```
┌ 基本信息：title/description/severity/confidence/cwe_id/source_rule_id ┐
├ 代码上下文：Monaco 只读，加载 location.file_path 对应片段（V1 文本，   │
│             V1.1 经 storage 文件服务取源码——Q5）                      │
├ 证据链：evidence.data_flow[] 步骤条（proto FlowStep：file:line + 说明）│
├ AI 判定：ai_verdict/ai_confidence/ai_reasoning —— reasoning 必须原文   │
│         展示；LLM 未接入时显示后端写入的 NEEDS_MANUAL 原因（P3 示范）   │
├ 修复建议：ai_fix_suggestion；MANUAL_REVIEW_REQUIRED 前缀 → 黄色横幅    │
└ 人工裁决区：6值 verdict + comment → PUT verdict；操作留痕（updated_at）┘
```

**⑤ 融合视图 `/tasks/:id/fusion`（模式A/C/D，ADR-182/184）**

数据即 findings 本身（dedup_group/matched_findings/is_unique 是 UnifiedFinding 字段，proto L84-86）：按 `dedup_group` 分组渲染卡片组——组内 primary（SAST 主发现）展开，成员以 chips 显示 matched_findings；`is_unique=true` 单独"AI 独有/单工具独有"分区。**不展示任何页面计算的"融合分"**（P2）。

**⑥ 对比视图 `/tasks/:id/comparison`（模式E，P1，ADR-182/184）**

- `GET /v1/tasks/{id}/comparison-report`（proto ComparisonReport.summary：四象限计数 + ComparisonMetrics 七指标）→ 韦恩图 + 指标表。
- **指标语义必须随图披露**（对齐 ADR-133 口径）：sast_precision/recall/f1 以 AI 发现为参照集，反之亦然；页脚固定说明"此为模式E互为参照的自洽指标，非 DiverseVul 基准 F1"（ADR-182/184）。
- disagreement 列表下钻到发现详情。

**⑦ 审核视图 `/tasks/:id/review`（旧模式D，已弃用；历史任务兼容）**

`ReviewSASTResults` 产物经任务上下文/报告获取：OverallAssessment（quality_score/conclusion/summary）+ 逐条 FindingReview（opinion 四值 CONFIRM/SUGGEST_REVIEW/QUESTION/REJECT + reasoning）。**零 LLM 参与时后端返回 NEEDS_REVIEW + quality_score=0，UI 必须原样呈现并显著提示"本轮审核未使用 LLM"**（ADR-128 的 UI 侧落实）。

**⑧ 报告中心 `/reports`（P1）**：`GET /v1/reports`（按 task/project 筛选）；格式 JSON/HTML/CSV/PDF（proto ReportFormat 四值，HTML→在线预览 iframe 沙箱+nonce CSP，PDF/CSV 直接下载）；`GET /v1/reports/{id}/download`（网关聚合 ReportChunk 流）。FAILED 报告显示失败原因与"重新生成"（GenerateReport 幂等修复后可重试，b1b6908）。

**⑨ 通知中心 / 知识库 / 管理**：通知=storage ListNotifications+MarkNotificationRead；↪KG 页已删（KG 六 RPC 随 ADR-197 出栈——ADR-206 回填）；Skills 页展示 ListSkills（**DSHRuntimeService**，03 §1.5——原标注 knowledge-service 系误）与热加载时间；用户管理 P1 已随 ADR-205 升级为列表+建号+停启用+重置密码（Q2 裁决更替，见 §11）。

### 3.4 实时能力演进路径（V1 → V1.1）

| 阶段 | 机制 | 前提 |
|---|---|---|
| V1 | GetTaskProgress 3s 轮询（终态自停）；通知 60s 轮询 | 无（现契约已支持） |
| V1.1 | gateway SSE：`GET /v1/tasks/{id}/watch` ↔ proto WatchTaskProgress 服务端流 | task-service 实现 Watch（现为诚实 Unimplemented）+ gateway 流式转码扩展 |
| V1.x | 文件上传/下载（proto 客户端/服务端流）经网关：下载=流聚合转发，上传=分块串行 POST | 网关流式扩展 |

### 3.5 统一 UX 约定

- **错误映射**：网关 gRPC→HTTP 映射（transcode.go）→ UI 文案表：400=参数错误(表单校验提示)、401=静默刷新/跳登录、403=权限不足页、404=空态插画、409=冲突（幂等键/状态机）→ 提示刷新重试、501=「能力未接入」专用组件（灰卡+说明+文档链接，P3）、503=降级横幅（服务暂不可用，自动重试 3 次退避）。
- **空态**：每种列表页定义空态文案与下一步动作（如无任务→引导创建向导）。
- **加载**：骨架屏；全局请求去重（TanStack Query key 规范）。
- **时间**：全部 UTC ISO8601 展示为本地时区（proto Timestamp）。

## 6. Webhook 出站（CI/CD 集成；↪"00 §交付物"引用已随 ADR-180 撤销——ADR-206 更正）

归属：storage-service NotificationService 的投递通道扩展（03 §83 已定义三通道：邮件/Webhook/站内），展现层文档定义其对外契约：

- **订阅管理**：V1 承载于**全局配置文件** `configs/codeaudit.yaml` 的 `webhook.subscriptions` 段（Q6 裁决修订：不使用分散的 K8s ConfigMap——全项目可调值统一进全局配置文件，见 ADR-137）；V1.1 项目级自助订阅需 proto 扩展（Q6 备案）。
- **事件集**=Kafka 五事件（01 §4.3）：`task.created / task.stage.completed / task.completed / finding.created / finding.verdict.updated`；payload = 事件消息的 protojson（snake_case），附 `X-CodeAudit-Event`、`X-CodeAudit-Delivery`（UUID 幂等）、`X-CodeAudit-Signature: sha256=HMAC(secret, body+timestamp)`。
- **可靠性**：失败重试 5 次 / 指数退避（对齐 07 §8 通知行），幂等键防重投；接收方 2xx 即成功。
- **安全**：HTTPS 强制；secret 每订阅独立；签名时间戳 ±5min 防重放。

## 7. 网关转码路由总表（UI 全量需求 → REST → proto RPC）

> 现有 transcode.go 已覆盖：auth 三件套、projects CRUD+config、tasks CRUD+submit/approve/start/cancel/retry/complete+progress、findings list/get、reports list/get。下表列出**需扩展的路由**（全部映射既有 proto RPC，零 proto 变更；R1）：

| REST（建议） | proto RPC（后端） | 消费方 | 备注 |
