## 1. 统一任务状态机 <!-- consumers: TP05,TP11 -->（全部模式共用）

> **2026-09-01 修订（人类批准，实现事实源 ADR-171）**：审批流（SubmitTask/ApproveTask/RejectTask）
> 整体废除——有创建权限即有启动权限，CREATED 经 StartTask 直达 RUNNING；
> PENDING 枚举值在 proto 中保留（历史数据兼容），不再产生。

```
CREATED ──StartTask──▶ RUNNING ──▶ COMPLETED
                         │
                         ├─▶ FAILED ──自动重试≤2──▶ QUEUED ──StartTask──▶ RUNNING
                         │        └─重试耗尽─▶ DEAD（仅人工RetryScanTask）
                         ├─▶ TIMEOUT（超时对账，每小时）
                         └─▶ CANCELLED（任何状态可取消）
```

- 枚举以 proto V2.0 `TaskStatus` 为准（含 CREATED=8、TIMEOUT=7、DEAD=9；PENDING=保留值）；
- 对账任务每天 02:00 全量扫描长时间 RUNNING 任务（>见 07 §8 超时上限）转 TIMEOUT 并触发部分结果落盘。

## 2. Saga 编排 <!-- consumers: TP05,TP08,TP11 -->（task-service 内实现，阶段编号与状态机对齐）

| Saga Step | 动作 | 失败补偿 |
|-----------|------|---------|
| S1 | CreateScanTask | 删除 ScanTask |
| S2 | StartTask 启动确认（CREATED→RUNNING；审批流已废除，ADR-171） | 标记 FAILED |
| S3 | 启动并行阶段（状态→RUNNING） | 更新 FAILED |
| S4a | AnalyzeCode（10m，3次重试） | 取消分析 |
| S4b | RunMultipleScans（20m，3次重试） | 取消扫描 |
| S5 | 并行汇合等待（超时见 07 §8） | 标记 TIMEOUT，返回已完成侧部分结果 |
| S6 | RunAIAnalysis / ReviewSASTResults（幂等） | 取消推理，销毁 OpenShell 沙箱 |
| S7 | FuseResults（模式A/C；幂等；旧B 冻结兼容） | 返回原始未融合结果 |
| S8 | BatchCreateFindings/BatchUpdateFindings（幂等） | 删除已存储结果 |
| S9 | 发布 `task.completed` 到 Kafka | 通知补偿：定时重试投递 |
| S10 | 报告生成（Kafka 异步消费） | 删除报告文件，允许重新生成 |

> 报告生成统一走 S9 Kafka 主路径（ADR-006）。

## 3. 五模式流程定版 <!-- consumers: TP05,TP06,TP07,TP08,TP09,TP11 -->

> **★修订注（2026-09-03，人类批准，ADR-186）**：四模式矩阵扩展为五模式——新增
> **D=AI增强SAST**（`SCAN_MODE_AI_ENHANCED_SAST=5`：SAST 多工具扫描 → **同文件同段去重** →
> 逐条 DSH 沙箱验证 → SAST+AI 判定汇总 → 融合报告；复用 VerifySASTResults，原 4a 能力激活）；
> 原 D（SAST+AI 并行对比）改称 **E=模式E**（`SCAN_MODE_COMPARE=7`，枚举值与流程不变，仅字母口径变更）。
> A/B/C 与两弃用值不变。01/03/07/10/14 模式口径同批对齐。
>
> **★修订注（2026-09-02，人类批准，ADR-182）**：四模式矩阵按人类决策重排——
> **A=纯SAST**（多工具并行审计→去重合并产出）/ **B=纯AI**（原"模式A"流程不变）/
> **C=SAST+AI 并行→融合去重输出**（默认推荐）/
> **E=SAST+AI 并行→单SAST/单AI/SAST+AI 三分桶同维度对比**（ADR-186 前称"模式D"）。
> 原 B（SAST→AI增强）与原 D（SAST→AI审核）**弃用**：枚举值保留兼容历史任务，编排分支冻结保留（§3.6），
> UI 新建入口不再提供。C/E 共用并行审计段（编排层 runModeParallel）。

### 3.1 模式A：纯SAST（SAST_ONLY）

```
阶段1 任务创建（附 sast_tools 多选）
阶段2 SAST并行扫描: Task→sast-adapter.RunMultipleScans（多工具并行执行，ADR-182）
   → UnifiedFinding[] → ResultService 落盘；SAST 全部失败 = 任务失败（唯一内容来源）
阶段3 去重合并: Task→SASTFusionService.FuseResults（AI 集为空，仅用融合管线的
   合并/去重/分组段：跨工具同位置去重对齐）→ 融合后单一清单
阶段4 报告: Kafka task.completed → ReportService（统一路径）
```

无 AI 环节、无代码分析（CPG）环节；五模式中速度最快（工具级，秒~分钟）。

### 3.2 模式B：纯AI（AI_ONLY）

```
阶段1 任务创建: Gateway→TaskService.CreateScanTask（CREATED；StartTask 后 RUNNING，审批流已废除 ADR-171）
阶段2 代码预处理: Task→dsh-runtime(CodeAnalysisService.AnalyzeCode) → CPG+AST+语言统计
阶段3 AI推理: Task→DSHRuntimeService.RunAIAnalysis
   五Agent流水: Code Analyst → Vuln Detector(知识双层: Skills→KG→RAG) → Severity Assessor
                → Fix Advisor → Quality Validator
   LLM语义分析: 沙箱内 headless DSH 整项目审计（ADR-140/173）；沙箱不可用→
              dsh-runtime 内置 RuleScan 兜底（ADR-175，降级显式标注）
阶段4 结果落盘: DSH→ResultService.BatchCreateFindings(幂等)
阶段5 报告: Kafka task.completed → ReportService（统一路径）
```

### 3.3 模式C：SAST+AI 并行融合（PARALLEL）★默认推荐

```
阶段1 任务创建（附 sast_tools）
阶段2 并行审计（C/E 共用段，互不交叉）:
   [SAST侧] Task→sast-adapter.RunMultipleScans（多工具并行）→ ResultService 落盘
   [AI侧]  Task→DSHRuntimeService.RunAIAnalysis（沙箱 DSH 整项目语义审计，降级链同模式B）
   部分结果语义（S5）: 两侧皆败→任务失败；单侧失败→如实标注降级继续
阶段3 融合去重: Task→SASTFusionService.FuseResults（过滤误报→合并→跨源去重对齐→置信度融合）
   → 融合后单一清单（SAST+AI 合并去重；融合失败→原始结果保留，任务不失败 07 §10）
阶段4 报告: Kafka task.completed → 融合报告
```

### 3.4 模式D：AI增强SAST（AI_ENHANCED_SAST）<!-- ADR-186 新增（人类决策 2026-09-03） -->

```
阶段1 任务创建（附 sast_tools）
阶段2 SAST并行扫描: Task→sast-adapter.RunMultipleScans（同模式A 内容来源段）
   → UnifiedFinding[] → ResultService 落盘；SAST 全部失败 = 任务失败（唯一内容来源）
阶段3 逐条沙箱验证: Task→DSHRuntimeService.VerifySASTResults（原 4a 能力激活，ADR-186）
   同文件同段去重（进沙箱前）: 按文件分桶→行区间扫并（±2 行容差吸收跨工具行漂移）→
     一组只发一轮沙箱 prompt（代表条目=severity 最高/行号最小，附注同段其余工具主张），
     判定广播回组内全部发现（reasoning 带"同段判定"溯源前缀）；契约不变（每 finding 一条判定）
   执行形态（ADR-173）: 整项目上传沙箱磁盘，逐组 prompt 交 DSH 自行阅读完整源码
     核对数据流/净化器/可达性，逐组取回单行 JSON 判定（TRUE_POSITIVE/FALSE_POSITIVE/
     UNCERTAIN + confidence + 理由），全部完成后销毁沙箱
   降级（07 §10）: 沙箱不可用 → 如实全批 NEEDS_MANUAL（显式降级标注，任务不失败）
阶段4 AI判定回写: Task→ResultService.BatchUpdateVerdict（幂等；失败降级不中断）
阶段5 融合汇总: Task→SASTFusionService.FuseResults（AI 集为空——AI 产出是判定而非新发现；
   误报过滤段此时已能消费 ai_verdict）→ 汇总 SAST+AI 判断
阶段6 报告: Kafka task.completed → 融合报告（含 AI 判定分布统计）
```

**边界**：不调 AnalyzeCode（无 CPG 段）、不做漏报搜索（与弃用的旧模式B 的差异——本模式
聚焦"验证 SAST 已报项"而非"补充 AI 新发现"）；报告阶段与模式C 同构。
定位：比 C 少一轮 AI 全项目审计、多一轮逐条精判——适合"SAST 结果可信度优先"的场景。

### 3.5 模式E：SAST+AI 并行对比（COMPARE）<!-- ADR-186 前称"模式D"（ADR-182），流程不变 -->

```
阶段1 任务创建（附 sast_tools）
阶段2 并行审计: 与模式C完全相同（共用段；两侧各自独立完成，不交叉验证）
阶段3 三分桶对比: Task→SASTFusionService.CompareResults（同文件同区域对齐）→
   单SAST / 单AI / SAST+AI 三类同维度对比（共同发现中结论相左计入分歧副注）
   + CalculateMetrics（互为参照 P/R/F1，ADR-133 口径）
阶段4 报告: Kafka task.completed → 对比报告（三分桶+指标+差异说明）
```

**C/E 边界**：并行审计段完全共用，仅输出形态不同——C 合并为单一清单（日常审计主路径），
E 保留两侧独立产出供同维度对比（能力评估/工具选型）。

### 3.6 已弃用模式（ADR-182，历史兼容冻结）

> 以下两模式 2026-09-02 起弃用（人类决策 ADR-182）：枚举值保留兼容历史任务，编排分支冻结，
> UI 不再提供；其服务端能力（VerifySASTResults/SearchMissedVulns/ReviewSASTResults）保留在契约中。
> 其中 VerifySASTResults 自 ADR-186（2026-09-03）起被 §3.4 模式D（AI增强SAST）复用激活。

**旧模式B：SAST→AI增强（TRADITIONAL_FIRST）**

> **2026-09-01 修订（人类批准，实现事实源 ADR-176）**：阶段4 按实际执行形态改写——
> 4a 的"读代码→数据流→净化器→可达性"是逐条 prompt 中的**验证语义判据**，实际由沙箱内 DSH
> 整项目逐条审查执行（ADR-173），非服务端四个独立程序分析步骤；4b 补沙箱通道与降级链；
> 4c 修复建议在模式B 未实现；4d 注明实际调用方。细节见下方★修订注。

```
阶段1 任务创建（同A，附sast_tools）
阶段2 并行: [2a] Task→sast-adapter.RunMultipleScans → UnifiedFinding[]→ResultService落盘
            [2b] Task→dsh-runtime.AnalyzeCode → CPG
阶段3 汇合（S5等待两者完成，才可进入阶段4）
阶段4 AI增强: Task→DSHRuntimeService
   4a VerifySASTResults: 逐条验证（语义判据: 读代码→数据流→净化器→可达性，见★）
      → ai_verdict/ai_confidence
   4b SearchMissedVulns: 全项目AI审计（未覆盖区域/复杂数据流/业务逻辑，见★）
      → 新增finding(source_tool=ai_agent)
   4c 修复建议: 模式B未实现（见★；契约字段预留）
   4d BatchUpdateVerdict(task-service回写)/BatchCreateFindings(dsh-runtime直写)（幂等）
阶段5 融合: Task→SASTFusionService.FuseResults（过滤误报→合并→去重对齐→置信度融合）
阶段6 报告: Kafka task.completed → 融合报告（含误报统计+AI独有发现）
```

**注**：ai_verdict 采用 6 值枚举（proto AIVerdict）；V1.x 阶段描述中的"3 值简化版"仅为 UI 分组视图（真阳性组/误报组/待人工组），不是枚举定义。

**★修订注（2026-09-01 按实际修订，人类批准，ADR-176）**：
- **4a 执行形态**（ADR-173）：沙箱内 DSH 整项目审查优先——项目源码打包经沙箱管理器（openshell-manager /files，沙箱基础设施，非9服务域）上传，逐条 prompt 告知项目路径+文件/行/规则/CWE/标题/疑点，DSH 自行阅读完整源码核对数据流/净化器/可达性，逐条取回单行 JSON 判定（TRUE_POSITIVE/FALSE_POSITIVE/UNCERTAIN + confidence + 理由），全部完成后销毁沙箱；任一回合失败/沙箱不可用 → **如实全批 NEEDS_MANUAL**（原 ai-inference 直连降级链已删——其自 ADR-140 起本就只能拿到规则占位、无真实 LLM，ADR-173 补遗②；删除裁决 ADR-175），不产生未经推理的确认结论（2026-08-27 诚实化纪律）。
- **4b 执行形态**（ADR-173）：沙箱单 prompt 全项目审计优先——新发现 source_rule_id=dsh-sandbox、判定 LIKELY_TRUE 且如实标注未经二次验证；实体由 dsh-runtime 直写 result-service。沙箱不可用 → dsh-runtime 内置 RuleScan 本地兜底（ADR-175：原 ai-native 直连/RuleScan RPC 段删除，RuleScan 内嵌 dsh-runtime，降级显式标注）。
- **4c 未实现**：模式B 判定链不产出修复建议——VerifiedFinding.fix_suggestion 与 UnifiedFinding.ai_fix_suggestion 契约字段预留未填，编排器无 4c 步骤；修复建议目前仅模式A 五Agent流水经 RunAIAnalysisResponse.fix_suggestions 产出。阶段6 原措辞"+修复建议"已随之删除。

**旧模式C：并行对比（原 PARALLEL 语义）**：ADR-182 起 PARALLEL 枚举改承载"并行→融合"（§3.3），
原"并行→四象限对比"语义由 SCAN_MODE_COMPARE 承载（§3.5，三分桶口径）；四象限中的"结论冲突"
在新 E 中作为共同发现内的分歧副注。

**旧模式D（SAST_REVIEW，已弃用）**：SAST→AI 审核四阶段流程块已删（ADR-182 弃用该模式、

## 5. 增量扫描机制 <!-- consumers: TP12,TP15 -->

```
project-service: 记录项目 commit 基线（上次扫描的 commit_id）
task-service:    创建任务时 diff 两次commit → changed_files 列表，写入TaskContext
AnalyzeCode:     changed_files 非空 → 仅对变更文件重建CPG子图，并与存量CPG合并；
                 为空 → 全量构建（首次扫描/基线丢失/合并冲突时自动降级全量）
SAST侧:          sast-adapter 按 changed_files 过滤扫描范围（工具支持时传路径参数）
```

## 6. 降级策略（数值与完整判定见 07 §10）

SAST工具失败→跳过继续；DSH超时→部分结果；KG/RAG不可用→Skills层兜底；LLM不可用→RuleScan规则引擎；融合失败→原始结果；CPG失败→AST降级；Kafka不可用→报告gRPC直调（幂等键保证不重复）。
